## 第 1 轮（2026-08-13）：物品修改类事件 — 货运接线

**范围**：全部带 ItemStack setter 的事件类校验一致性排查 + CargoNetworkTask 物品流端到端审计。

**排查结果（无问题）**：
- 约 190 个事件带 setter；物品类 setter 几乎全部有 `Validate.notNull`/`Objects.requireNonNull`；`AndroidFarmEvent.setDrop` 的 `@Nullable` 是有意设计（文档注明）
- 基座 place/take 接线：消耗手物品→展示替换物→取回替换物，闭环无 dup；取消语义正确
- 货运撤回/插入接线：取消退回来源槽、替换物分发、异常时物品回退（try/catch + insertItem 兜底），无 dup/吞没

**发现并修复**：
- `fix(cargo)`（8e7518c）：`CargoItemInsertEvent/WithdrawEvent.setItem(AIR)` 语义依赖落地路径——vanilla 容器路径把空气"插入"空格视为传输完成（物品凭空消失），其它路径退回来源，行为不一致。统一为：替换物为空气/空栈 = 销毁物品。补 Javadoc。
- 新增 `TestCargoNetworkTaskItemFlow` 7 项端到端接线回归（同包反射直驱 routeItems；CargoNet mock 掉 attached block/filter/regulator，物品流走真实代码与箱子库存）

**遗留观察（后续轮次）**：
- 基座 `placeItem`：setItem(AIR) 会先消耗手物品再尝试生成空气展示实体（addon 误用面，非客户端可利用），可同样归一化
- `SmeltersPickaxeSmeltEvent`/`SlimefunMobDropEvent` 等 setter 仅 notNull、未拒空气——确认各落地路径对空气的行为是否一致

## 第 2 轮（2026-08-13）：数值修改类事件 — 边界/溢出校验

**范围**：两批共约 40 个事件的数值/向量/对象 setter 校验一致性 + 消费侧循环与算术安全性。

**排查结果（无问题）**：
- 绝大多数 setter 有领域对齐校验（EnergyConsumeEvent 封顶 maxTransfer、InfernalBonemealGrowEvent 封顶 maximumAge、CargoNodeChannelChangeEvent 限 0-15、BackpackCreateEvent 限 9-54 的 9 倍数等）
- `AnimalAccelerateEvent.setAgeBoost` 无校验系**有意设计**（Javadoc 注明负值使动物返幼）
- `MagicEyeOfEnderLaunchEvent.setVelocity(null)`/`StomperBootsPushEvent.setPushVelocity(null)` 落地路径均有 null 分支回退默认行为，@Nullable 语义成立
- Crop/Animal 加速器消费侧有 Math.min 钳制或 setAge 语义安全

**发现并修复**：
- `fix(events)`（84e3fa0）：`TreeAccelerateEvent.setGrowthBoost` 仅校验非负，消费侧按 boost 循环 `applyBoneMeal`（tick 线程），异常大值卡死服务器 → 新增 `MAX_GROWTH_BOOST=100` 上限校验
- 同提交：`StomperBootsPushEvent.setDamage` 无校验，NaN/无穷伤害写入实体生命状态 → 拒绝非有限值

**遗留观察（后续轮次）**：
- 向量类 setter（GrapplingHookFireEvent.setDirection、WindStaffLaunchEvent.setVelocity 等）未校验 NaN 分量——NaN 速度可能触发玩家踢出/物理异常（addon 误用面），可作专项加固轮
- `StomperBootsPushEvent.setDamage` 负值未拒（Bukkit 语义下近似无效），暂保留

## 第 4 轮（2026-08-13）：并发与异步 — 事件线程声明契约

**范围**：全量 ~200 个新事件的触发点线程上下文 vs `Event` 构造器的 async 声明。

**线程模型核实**：TickerTask/机器 BlockTicker/盔甲三任务（SlimefunArmor/Radiation/RainbowArmor 均 runTaskTimerAsynchronously）/AutoSavingService 为异步；CargoNetworkTask 经 runSync 回主线程；玩家任务（Jetpack 等）与 AncientAltarTask/MiningTask 为主线程。

**发现并修复**：
- `fix(events)`（b362d6a）：45 个从异步 ticker 线程触发的事件以同步构造器声明，`isAsynchronous()` 误报 false → 统一自适应 `super(!Bukkit.isPrimaryThread())`（含 3 个 this() 委托构造器特判、2 个 PlayerEvent 双参形式）。此前仅 EnergyConsumeEvent 等 6 个事件有自适应声明，属遗漏
- 全量 3029 项测试通过、0 失败

**遗留观察（后续轮次）**：
- 事件在异步线程触发意味着**附属监听器也在异步线程执行**——属文档级契约（各事件 Javadoc 多数已注明 ticker thread），可在发布说明中统一提示
- BlockStorage/PlayerProfile 并发模型已在 4.9.4 加固（CME/纪元/dirty 可见性），本轮未复发

## 第 5 轮（2026-08-13）：高负载稳定性 — 每 tick 分配 / 无界增长 / 日志风暴

**范围**：全部新事件触发点的监听器守卫（`getRegisteredListeners().length > 0`）核查；新代码路径的无界集合增长；日志风暴面。

**排查结果（无问题）**：
- TrashCanVoidEvent 已有监听器守卫（TrashCan.java:73，包裹整个收集+触发段）；此前粗扫因守卫距 callEvent 超 8 行误报
- 其余无守卫触发点均为上游既有（MachineProcessor/FarmerAndroid/MinerAndroid 的旧事件，按操作完成触发而非每 tick）或灾难低频路径（ReactorExplodeEvent）
- CargoNetworkTask ownerCache 为每任务每 tick 局部、有界；MenuListener.menus 关界面即清；ItemFilter 失败重试有 MAX_FAILED_UPDATES=3 封顶
- 新代码零日志调用（api/events 包无 logger；分支改动文件中 3 处 "warning" 均为 Javadoc 文字），无日志风暴面

**发现并修复**：
- `fix(cargo)`（80eb524）：TrashCan 豁免匹配误用 `ItemStack#equals`——Bukkit equals 只比类型/数量/耐久、忽略 meta。两槽位放同型同量不同 meta 物品（如一把普通镐 + 一把命名镐），监听器赦免命名镐时，先扫描到的普通镐会"等于"赦免项被保留，**真正点名的命名镐反被销毁**（数据丢失）。修复：tick 内保留收集时的物品引用与槽位映射、按原引用身份匹配（监听器传入的正是这些引用），兜底用 `SlimefunUtils.isItemSimilar`（meta 感知）+ 数量相等覆盖防御性克隆。回归测试：meta 区分槽位赦免精确性
- 测试环境确认（已入记忆库）：MockBukkit 下 `ItemStack.isSimilar` 同样不区分 display name，物品比较一律用 SlimefunUtils.isItemSimilar

## 第 6 轮（2026-08-13）：领地保护闭合 — 新增事件路径的权限校验

**范围**：全部"改变世界"动作的新事件触发点 vs ProtectionManager 校验的先后次序、setter 是否可使已通过的校验失效、cancel veto 完整性（子代理全量核查 + git diff 确认本分支零删除/移动校验）。

**排查结果（OK）**：
- 机器人全系列（Mine/ChopTree/Farm/Attack/ItemDeposit/Refuel/Move）：校验一律在事件之前、逐目标（方块/实体）进行；事件无可改变被校验对象的 setter；cancel 正确跳过动作。无 owner 的旧机器跳过校验为 merge-base 已有历史兼容行为
- InfusedHopper（吸取前按物品位置校验）、基座 place/take（usePedestal 入口校验）、AutoBreeder（逐实体校验）、BlockPlacer（owner + PLACE_BLOCK）：均闭合
- 本就无需校验：FisherAndroid（不改世界）、SoulboundItemsKeepEvent（仅自身物品）、OilPump/GEOMiner（区块虚拟储量，GUI 已有 INTERACT_BLOCK）

**发现并修复**：
- `fix(blocks)`（41b8fd4）：`BlockPlacerPlaceEvent.setItemStack` 生效于 `isAllowed()` 之后——addon 可把已核准材料换成非方块（setType 抛异常）或 unplaceable-blocks 黑名单材料，绕过服务器配置。两个落地路径（vanilla/SF 方块）现对替换物重跑 isAllowed，不合格整体跳过、不消耗物品 + 回归测试
- `fix(events)`（b69b286）：`AsyncEntityAssembleEvent.setSpawnLocation` 零校验——null 世界/NaN/无穷坐标传入同步生成任务会损坏生成。setter 校验世界非空、坐标有限（跨世界重定向仍允许）。Wither 生成点重定向无领地校验属历史如此（Assembler 无 owner 记录），已记录

**遗留观察（后续轮次）**：
- AbstractEntityAssembler 无 owner 跟踪，生成动作天然无法做 ProtectionManager 校验；如需闭合需引入 owner 记录（功能变更，超本轮范围）
- GEOMiningCompleteEvent cancel 时产物被丢弃而非返还（设计选择，Javadoc 已注明）

## 第 7 轮（2026-08-13）：数据持久化损坏容错

**范围**：本分支改动文件中全部 BlockStorage/PlayerProfile/Config 读取解析点对损坏数据（缺键、null、类型错误）的容错（子代理全量核查 + diff 确认本分支未改任何解析逻辑）。

**排查结果**：本分支**零引入/零加重**——改动均为事件注入层，不触碰持久化解析；货运 channel/owner、安卓 fuel/index/rotation、全息 offset、经验收集器、Research 读取、waypoint 读取侧等容错均良好（安全回退或 per-entry 隔离）。

**发现并修复（3 条上游既有数据丢失 BUG，loop 指令要求修复一切数据操作 BUG）**：
- `fix(assembler)`（47b07cb）：AbstractEntityAssembler 的 offset 键缺失时 `Double.parseDouble(null)` 抛 NPE 绕过 NumberFormatException catch，且解析在 consumeResources 之后——每个失败 tick 白吃整套材料+电量，连续 4 次报错被 TickerTask 摧毁机器。修复：解析前置、null/NFE 均安全跳过不消耗；GUI 两处读取统一走带回退默认值的 getSpawnOffset
- `fix(blocks)`（492a627）：BlockPlacer 的 owner 字段为非 UUID 字符串时 `UUID.fromString` 抛异常且发生在 setCancelled 之前——退化为原版发射器、物品以弹射物损失。修复：解析失败与 owner 缺失一致失败关闭
- `fix(storage)`（7d6d60d）：LegacyStorage 背包 size 非数字时 getInt 返回 0 → 按空背包加载 → 下次保存清空内容（连锁丢数据）。修复：size<=0 时从最高内容槽位推断尺寸（9 的倍数、封顶 54）；无内容可推断则跳过并告警
- 附带 `docs(research)`（7d8b85b）：meetsDependencies javadoc 与代码相反——profile 未缓存时实际返回 false（失败关闭，安全侧），以代码为准修文档

**遗留观察（后续轮次）**：
- ItemFilter 的 filter-type 损坏时被静默当作黑名单（语义翻转、物品流向改变但不崩溃不丢数据），预期语义待定
