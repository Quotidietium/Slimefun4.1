## 第 2 轮（2026-08-27）：新 API 可用性——研究系统数字 id 的持久化碰撞（2 项修复，其中 1 项 HIGH）

**背景**：目标要求把 5.0.0 新增 API 的可用性/稳定性作为审查重点。本轮从 `ResearchBuilder`（5.0.0 新增流式构建器）切入，核实其与存储层的交互。

**关键事实核实**：本 fork 的活跃存储实现仅有 `LegacyStorage`——研究解锁状态以**数字 id 为持久化键**（`researches.<id>`，读写均在 LegacyStorage:44/167）。因此数字 id 的唯一性是数据完整性的硬约束，而不仅是"遗留兼容字段"。

**发现并修复（2 项）**：

1. `fix(api)`（35cba9c72，HIGH）：**ResearchBuilder 默认 `id=0` 与持久化键碰撞**——内置首个研究 walking_sticks 正是 id 0（ResearchSetup:37），任何用 builder 不调 `id()` 的附属研究都会与它（以及彼此）共享 `researches.0`：解锁 walking_sticks（几乎人人解锁的第一个研究）即免费解锁所有默认 id 的附属研究，反向亦然。修复：未显式指定 id 时从 `NamespacedKey` 确定性派生（`floorMod(hashCode, 2^30)`，跨重启稳定、避开内置 0-8800 密集段）；`id()` Javadoc 更新。既有测试全部显式传 id，此默认路径此前零覆盖（漏检原因）
2. `fix(storage)`（e2d5f3d7b，HIGH，上游既有）：**内置 coal_generator 与 bio_reactor 共用 id 173**（upstream/experimental 同款，上游保存侧注释自认 hack 绕过）——解锁其一即双双永久解锁（14 级研究白送 18 级研究）。修复三件套：
   - bio_reactor 重编号 173→1730（静态核验 ResearchSetup 全部 id 唯一，仅此一处重复）
   - LegacyStorage 加载侧兼容：老存档 `researches.173` 存在时同时恢复两个研究（保留玩家既有进度，不丢解锁）；下次保存起各自独立落键
   - `Research.register()` 新增重复 id 告警——把静默数据污染变为启动可见（防附属再引入）
   - 保存侧防御分支保留（防未来任意重复 id），过时注释更新

**确认无问题**：
- `ResearchBuilder` 其余面：必填字段校验（key/name notNull、cost≥0）、LinkedHashSet 保序、build/register 分离语义正确；既有 10 项测试覆盖
- 研究依赖系统（addDependency/meetsDependencies/unlock 强制）：r9/r11 已深审，本轮无复发
- `SlimefunWeapon`/`SlimefunFood` 标记接口：纯标记无状态，TestSlimefunCombatEvents/TestSlimefunFoodEvents 已覆盖
- 保存侧清理分支（`anyMatch(getID()==)`）在重编号后对新旧数据均正确（测试第二段验证：解锁状态可独立撤销）

**测试**：新增 3 项（builder 派生 id 稳定且非 0/显式 id 保留、legacy 173 双恢复 + 独立撤销往返）；全量 **3156 项通过、0 失败、0 错误、7 跳过**（BUILD SUCCESS，Java 21，基线 3153→3156）。

**行为变更提示（发版须知）**：5.0.0-5.1.1 期间若有附属用 ResearchBuilder 默认 id 创建过研究，升级后其解锁状态按新派生 id 重新计算（旧 `researches.0` 状态本就与 walking_sticks 混淆，属污染数据）；coal_generator/bio_reactor 的既有解锁经兼容逻辑无损保留。

## 第 3 轮（2026-08-27）："数字 id 作持久化键"bug 类全项目推广清扫

**背景**：第 2 轮的两个 HIGH 均属"标识符默认值/重复值在持久化键上静默碰撞"。本轮把该 bug 类推广到全项目所有按数字 id 持久化的体系逐一核验。

**清扫结果（干净，第 2 轮两处为仅有实例）**：
- **背包 id**（PlayerProfile.createBackpack:397）：`max-key+1`（非 map.size，r68 已修），per-player 命名空间，lore 携带 `ID: <hash>#<id>` 读写两侧同源（第 1 轮已核）✓
- **机器人脚本 id**（ProgrammableAndroid.uploadScript:478）：`作者已传脚本数+1`——脚本体系 **append-only**（全代码库无删除路径），id 严格单调不碰撞；文件名嵌入作者 UUID（r14 已修路径穿越），跨作者命名空间隔离；同码防重传在 id 分配之前 ✓
- **传送点 id**（GPSNetwork）：字符串键、净化+空 id 拒绝（r12/r58 已审），非数字 id 体系 ✓

**回归**：本轮无代码改动；全量基线维持 **3156 项通过**（第 2 轮回归即本类闭合验证）。

## 第 6 轮（2026-08-27）：DirtyChestMenu/BlockMenu 多写入者槽位竞争专项 + GEO 供给并发复验（2 项修复，含 1 项实证并发丢更新）

**范围**：菜单体系的多写入者现实——异步机器 ticker（AContainer 等输出 pushItem/consumeItem）与主线程（玩家点击/cargo runSync/方块破坏 dropItems）操作同一 BlockMenu；GEO 供给 map 跨区块写入复验 r64 结论。

**发现并修复（2 项，提交 58061ef53）**：

1. **pushItem/consumeItem 丢更新窗口（并发实证）**：两个方法均为"读槽→改量→写回"的 check-then-act，无同步。8 线程同槽推入探针（200 轮）实证 **3 轮丢更新、共 11 个物品凭空消失**（两线程同时读到旧 amount，后写覆盖先写）。生产对应面：异步 ticker 推产出 vs 主线程 cargo/玩家交互同一机器菜单。修复：两方法加菜单实例级 `synchronized`——合并分支与 consumeItem 为纯菜单内操作零死锁面；null 槽分支的 `preset.onItemStackChange` 回调在锁内运行属已文档化取舍（默认实现纯函数；addon 不得在其内重入其它菜单，注释明示）。修复后探针 **0/200**。`replaceExistingItem` 保持不同步：其丢失窗口仅存于 null↔非 null 槽态跃迁的精确交错，且它是 addon 回调面，全面加锁的死锁/行为风险大于收益——记录为残留理论窗口
2. **pushItem 合并分支持久化缺失（数据丢失）**：合并分支原地 `stack.setAmount` 后**从不 markDirty**（r42"pushItem→replaceExistingItem→markDirty 链式完整"的结论只对空槽分支成立，予以纠正）——`BlockMenu.save` 以 `changes>0` 门控，菜单唯一改动为合并时永不重存，**重启丢物品**。受影响面：GEOMiner/收割机器人/砍树机器人等"只推产出不消耗输入"的机器（消耗型机器被同 tick 的 consumeItem markDirty 掩蔽）。修复：合并发生时补 `markDirty()`。新增确定性回归测试（模拟 save 后 changes=0，合并推入后必须 isDirty）
