# SlimeFun4.1 v5.1.x 审计追踪

延续 [5.0.0-audit.md](5.0.0-audit.md) 的 /loop 审计循环，覆盖 5.1.0（全面汉化）与 5.1.1 之后的新改动面。每轮覆盖不同方面，本文件记录已覆盖范围、发现与处置。

## 第 1 轮（2026-08-27）：5.1.0 汉化的逻辑闭合——双语兼容机制 + 字符串匹配契约全量核查

**背景**：5.0.0 审计循环（r1-r170）结束于汉化之前，5.1.0 是此后最大的一批改动（显示层/资源层全量替换）。本轮核查发布说明声称的兼容机制是否真实成立（"表述与实现相符"检查），以及汉化是否引入新的字符串匹配失配。

**4 处双语兼容机制逐条核实（全部成立）**：
1. **灵魂绑定行**（`SlimefunUtils:74-81`）：`isSoulbound` PDC+lore 双因子，lore 侧 `contains(SOULBOUND_LORE) || contains(SOULBOUND_LORE_LOCALIZED)` 新旧两行都认（整行 equals，符文 lore 里的句子不会误匹配）；`setSoulbound(false)` 两版都删；`setSoulbound(true)` 只写中文行 ✓
2. **剩余次数正则**（`PatternUtils.USES_LEFT_LORE`）：`§e[0-9]+ (Uses? §7left|次 §7剩余)` 与写入侧 `LoreBuilder.usesLeft`（`&e<N> 次 &7剩余`）格式精确一致，`matches()` 全行匹配成立；英文 `Uses?` 兼容单复数 ✓
3. **多功能工具模式行**（`MultiTool`）：`LORE_PREFIX`（中文）/`LORE_PREFIX_LEGACY`（英文）经 `Pattern.quote` 交替匹配，写入中文前缀 + stripColor 物品名，下次匹配闭环；越界回退与 `add(Math.min(2, size))` 守卫在位 ✓
4. **MOB_DROP 反解析**（`RecipeType.resolveEntityType`）：全项目 MOB_DROP 配方仅 1 处（铁傀儡，在别名表内）；猪灵图标实际走 `BARTER_DROP`（不解析名字），别名属防御性冗余；`toUpperCase` 对中文无操作，别名键稳定匹配 ✓

**其它字符串匹配契约核查（全部同源自洽）**：
- 充能行（`ChargeUtils`）：`LORE_PREFIX` 与 `REGEX` 同源常量，语言无关格式 `N / M J` ✓
- 背包 ID 行：模板 `&7ID: <ID>` 与 `AbstractCraftingTable:93/104/121`、`PlayerProfile:795` 匹配侧全部保留英文 ✓
- 刷怪笼 `Type: ` 前缀：模板保留英文，`getEntityType` 匹配不受影响 ✓
- 祭坛探针前缀 `§dALTAR §3Probe - §e`：保留英文， AncientPedestal/ItemPickupListener 两侧同源 ✓
- 研究烟花名 `"Slimefun Research"`：`FireworkUtils:49`（发射）与 `FireworksListener:42`（免伤比较）同源保留英文 ✓
- 固定索引 lore 读取：全项目仅 `KnowledgeTome` get(0)/get(1)，模板行结构与读写索引自洽，老英文存档同结构兼容 ✓
- 无任何 `getTitle()` 字符串比较（GUI 标题纯显示层，6 处硬编码标题已汉化无副作用）✓

**lore-phrases 动态翻译基础设施（显示层安全性核实）**：
- `translateLore` 返回新列表、`getLocalizedItem` 经 `CustomItemStack.create` 构造克隆——只作用于指南显示，实际物品 lore 不被污染（`Type: `/`ID: ` 存储契约不受"类型：/编号："显示翻译影响）

**本地化资源完整性（脚本核对）**：

## 第 2 轮（2026-08-27）：新 API 可用性——研究系统数字 id 的持久化碰撞（2 项修复，其中 1 项 HIGH）

**背景**：目标要求把 5.0.0 新增 API 的可用性/稳定性作为审查重点。本轮从 `ResearchBuilder`（5.0.0 新增流式构建器）切入，核实其与存储层的交互。

**关键事实核实**：本 fork 的活跃存储实现仅有 `LegacyStorage`——研究解锁状态以**数字 id 为持久化键**（`researches.<id>`，读写均在 LegacyStorage:44/167）。因此数字 id 的唯一性是数据完整性的硬约束，而不仅是"遗留兼容字段"。

**发现并修复（2 项）**：

1. `fix(api)`（35cba9c72，HIGH）：**ResearchBuilder 默认 `id=0` 与持久化键碰撞**——内置首个研究 walking_sticks 正是 id 0（ResearchSetup:37），任何用 builder 不调 `id()` 的附属研究都会与它（以及彼此）共享 `researches.0`：解锁 walking_sticks（几乎人人解锁的第一个研究）即免费解锁所有默认 id 的附属研究，反向亦然。修复：未显式指定 id 时从 `NamespacedKey` 确定性派生（`floorMod(hashCode, 2^30)`，跨重启稳定、避开内置 0-8800 密集段）；`id()` Javadoc 更新。既有测试全部显式传 id，此默认路径此前零覆盖（漏检原因）
2. `fix(storage)`（e2d5f3d7b，HIGH，上游既有）：**内置 coal_generator 与 bio_reactor 共用 id 173**（upstream/experimental 同款，上游保存侧注释自认 hack 绕过）——解锁其一即双双永久解锁（14 级研究白送 18 级研究）。修复三件套：
   - bio_reactor 重编号 173→1730（静态核验 ResearchSetup 全部 id 唯一，仅此一处重复）
   - LegacyStorage 加载侧兼容：老存档 `researches.173` 存在时同时恢复两个研究（保留玩家既有进度，不丢解锁）；下次保存起各自独立落键
   - `Research.register()` 新增重复 id 告警——把静默数据污染变为启动可见（防附属再引入）
   - 保存侧防御分支保留（防未来任意重复 id），过时注释更新

**确认无问题**：
- `ResearchBuilder` 其余面：必填字段校验（key/name notNull、cost≥0）、LinkedHashSet 保序、build/register 分离语义正确；既有 10 项测试覆盖
- 研究依赖系统（addDependency/meetsDependencies/unlock 强制）：r9/r11 已深审，本轮无复发
- `SlimefunWeapon`/`SlimefunFood` 标记接口：纯标记无状态，TestSlimefunCombatEvents/TestSlimefunFoodEvents 已覆盖
- 保存侧清理分支（`anyMatch(getID()==)`）在重编号后对新旧数据均正确（测试第二段验证：解锁状态可独立撤销）

**测试**：新增 3 项（builder 派生 id 稳定且非 0/显式 id 保留、legacy 173 双恢复 + 独立撤销往返）；全量 **3156 项通过、0 失败、0 错误、7 跳过**（BUILD SUCCESS，Java 21，基线 3153→3156）。

**行为变更提示（发版须知）**：5.0.0-5.1.1 期间若有附属用 ResearchBuilder 默认 id 创建过研究，升级后其解锁状态按新派生 id 重新计算（旧 `researches.0` 状态本就与 walking_sticks 混淆，属污染数据）；coal_generator/bio_reactor 的既有解锁经兼容逻辑无损保留。

## 第 3 轮（2026-08-27）："数字 id 作持久化键"bug 类全项目推广清扫

**背景**：第 2 轮的两个 HIGH 均属"标识符默认值/重复值在持久化键上静默碰撞"。本轮把该 bug 类推广到全项目所有按数字 id 持久化的体系逐一核验。

**清扫结果（干净，第 2 轮两处为仅有实例）**：
- **背包 id**（PlayerProfile.createBackpack:397）：`max-key+1`（非 map.size，r68 已修），per-player 命名空间，lore 携带 `ID: <hash>#<id>` 读写两侧同源（第 1 轮已核）✓
- **机器人脚本 id**（ProgrammableAndroid.uploadScript:478）：`作者已传脚本数+1`——脚本体系 **append-only**（全代码库无删除路径），id 严格单调不碰撞；文件名嵌入作者 UUID（r14 已修路径穿越），跨作者命名空间隔离；同码防重传在 id 分配之前 ✓
- **传送点 id**（GPSNetwork）：字符串键、净化+空 id 拒绝（r12/r58 已审），非数字 id 体系 ✓

**回归**：本轮无代码改动；全量基线维持 **3156 项通过**（第 2 轮回归即本类闭合验证）。

## 第 4 轮（2026-08-27）：高频新事件 API 附属开发者视角端到端契约演练 + 1.21.11 兼容面复查

**范围**：目标要求把新 API 可用性作为审查重点。本轮对三族最高频的新事件（EnergyGenerate / CargoItemWithdraw|Insert / AndroidMine）以"附属注册真实监听器 → 生产触发路径 → 修改/取消路径落地"的方式演练既有覆盖与缺口，随后复查 1.21.11 符号兼容面与本循环修复的热路径归属。

**三族覆盖盘点与补齐**：
- **Cargo 族（既有覆盖完备，无缺口）**：TestCargoNetworkTaskItemFlow 8 场景全部经真实 routeItems 驱动——无监听器传输/取消退回源槽/setItem 替换分发物/setItem 空气=销毁/插入侧对称三场景/监听器事件中途拆源容器不吞没
- **Energy 族（补齐 setValue 修改路径，新增 3 项测试全绿）**：既有覆盖为契约测试 + 结算 cancel/异常/池化/回存（TestEnergyNetSettlement），缺"修改值流经真实结算"。新增 `TestEnergyGenerateModificationDrill`（经 pluginManager 注册真实监听器 + 反射驱动真实 tickAllGenerators/storeRemainingEnergy）：
  - 倍增监听器：可见值（发电 10 + 池化存储 50 = 60）×2 → 真实 supply=120；余量回存与重写语义在修改后依然成立
  - 归零监听器（setValue(0) 非取消）：supply=0 且发电机仍属被结算集合（区别于 cancel 的 unpooled 保留语义）——与 Javadoc"缩放贡献量"契约一致
  - setEnergy(-1) 拒绝（Validate ≥0）
- **AndroidMine 族（MockBukkit 限制，代码检视验证）**：MockBukkit 3.133.2 的 `BlockMock.getDrops(ItemStack)` 抛 UnimplementedOperationException（javap 实证），真实 dig() 演练不可行（与第 9/18 轮同类限制，按惯例转代码检视）。检视确认：MinerAndroid.dig/moveAndDig 触发事件后消费侧 `breakBlock(menu, event.getDrops(), block)` 直读监听器可变列表——修改必然生效；TestAndroidEvents 已覆盖字段暴露/可变性/分发可见性（dispatch 层）

**1.21.11 符号兼容面复查（干净）**：

**热路径归属评估（免基准依据）**：本审计循环（第 1-4 轮）全部修复位于启动/加档/玩家消息路径——ResearchBuilder.build（附属启动期）、Research.register 重复扫描（启动期一次性 O(n²)，n≈250 即数万次 int 比较）、LegacyStorage.loadPlayerData（每次档案加载多一次已加载 Config 的 contains 查询）、MultiTool 消息（交互路径）。均不在 benchmark/ 覆盖的 tick 热路径（ticker-run/charge 写入/放置破坏/电容/全息）上，**无需重跑基准**。
