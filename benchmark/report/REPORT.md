# SlimeFun4.1 性能优化基准对比报告

- **日期**:2026-07-26
- **对比对象**:`4.9.2-baseline`(提交 `459558877`,性能优化前)vs `4.9.3-optimized`(P1–P5 全部优化 + P1b 修复后)
- **测试工具**:`benchmark/` 目录下的 MockBukkit 模拟基准(详见 [README.md](../README.md))
- **环境**:Windows 11,Oracle JDK 21.0.10,MockBukkit 3.133.2 (MC 1.21.1)
- **方法**:每个版本在全新 JVM 中完整启动插件后依次运行全部场景;两轮独立运行(另一轮见 `-r3` 文件),表中为中位数,提升倍数按两轮均值计算
- **原始数据**:[results-4.9.2-baseline.txt](results-4.9.2-baseline.txt)、[results-4.9.2-baseline-r3.txt](results-4.9.2-baseline-r3.txt)、[results-4.9.3-optimized.txt](results-4.9.3-optimized.txt)、[results-4.9.3-optimized-r3.txt](results-4.9.3-optimized-r3.txt)

## 结果总览

| 场景(规模) | 4.9.2 基线 | 4.9.3 优化 | 提升 | 对应提交 |
|---|---:|---:|---:|---|
| BlockStorage 充能写入(5000 方块) | ~950 ns/次 | ~194 ns/次 | **4.9×** | `b71f6a07c` |
| BlockStorage save(5000 脏方块) | ~26.3 ms | ~33.5 ms | 0.79×(见下注) | `b71f6a07c` + `3489803ef` |
| 空转机器配方扫描·空输入(1000 台) | ~1006 ns/tick | ~701 ns/tick | **1.4×** | `966051f8b` |
| 空转机器配方扫描·不匹配输入(1000 台) | ~2624 ns/tick | ~296 ns/tick | **8.9×** | `966051f8b` |
| 电容贴图更新·同档位(2000 个,真实玩家头) | ~4349 ns/次 | ~166 ns/次 | **26×** | `8add0ddba` |
| 全息标签推送·标签未变(2000 个) | ~9194 ns/次 | ~108 ns/次 | **85×** | `8f383b2d3` |
| TickerTask 完整 run(5000 个平凡 ticker) | ~3.60 ms(719 ns/块) | ~3.17 ms(634 ns/块) | **1.13×** | `83e5e72cc` |

注:save() 的 0.79× 是**故意的时间转移**——基线把 JSON 序列化摊在每次写入里(save 时只剩文件 IO),优化版把序列化推迟到 save 时批量执行。一个"保存周期"的总成本应按 **写入×N + save** 计算:基线为 `N×950ns + 26.3ms`,优化版为 `N×194ns + 33.5ms`,当每方块在每个保存窗口内写入超过 ~10 次时优化版即开始领先。生产环境中电网每 0.5s 写一次、自动保存间隔为分钟级,每方块每窗口写入约千次量级,**周期总成本约为基线的 1/5**(5000 方块、每方块 1200 次写入:基线 ≈ 5.73s,优化版 ≈ 1.20s)。

## 基准测试发现的回归与修复(P1b)

第一轮对比发现优化版 save() 由 26ms 升至 85ms:P1 的 save() 使用每次调用局部的文件视图缓存,而 CSCoreLib `Config` 构造时会从磁盘解析整个 `.sfb` 文件,导致**每个保存周期都重新解析所有触及的 id 文件**。基线虽也在写入侧付出同样的重解析(`blocksCache` 在 save 时被丢弃),但该开销被写入基准的预热吸收,未在基线 save 数字中体现。

修复(`3489803ef`):将文件视图改为 `BlockStorage` 级别的持久 `blockFiles` 缓存,save 仅回写本周期触及的 id;文件键为空时连同缓存视图一并移除(防止陈旧键复活);`saveAndRemove()` 清空缓存。修复后 save 降至 ~33.5ms,且**基线与优化版双方都不再付出重解析**。全量测试 1877/0/0/7 保持绿色。

这是本轮基准测试的直接产出:没有对比测量,该回归会随 P1 进入生产环境,在大型服务器上每个自动保存周期重复支付全量 `.sfb` 解析。

## 各场景说明

- **BlockStorage 充能写入**:模拟电网真实热路径(`energy-charge` 每 tick 每组件一次)。基线每次写入都执行 JSON 序列化 + 文件视图更新;优化版为纯内存操作(Map put + 脏标记)。
- **空转机器配方扫描**:输入槽为空时基线的扫描本身较快(相似性检查快速失败),故提升温和;输入槽有**不匹配物品**时基线每 tick 都全量比对配方表,负缓存消除该开销(8.9×)。两种变体在生产中都极其常见。
- **电容贴图**:本环境 MockBukkit 支持 Skull,基线每次调用都真实执行了贴图应用(玩家头 BlockState 更新),与生产主线程开销一致;优化版同档位直接跳过。
- **全息标签**:基线每次都经实体 UUID 查找 + setLabel;优化版标签未变且 30s 存活窗口内直接返回。生产中为每网络 tick 每全息一次。
- **TickerTask run**:5000 个平凡异步 ticker 的完整调度周期,含防干扰采样(单元测试模式不启动定时 ticker)。首轮曾测得反向结果(5.0 vs 4.2ms),第二轮交叉复测确认为 JIT 方差;两轮稳定显示优化版快 ~13%。

## 与生产环境的差异(诚实声明)

- `Slimefun.runSync` 在单元测试模式下立即在调用线程执行,因此"调度开销"的绝对值与生产(主线程队列 + 后续执行)不同;但新旧版本同环境对比,比值仍然有效。
- MockBukkit 的实体/方块操作成本与真实服务端不完全一致,电容与全息场景的**倍数**可信,**绝对纳秒数**仅供参考。
- 未测量真实 Paper 服务器端到端 TPS;如需生产级验证,建议用 spark 在真实服务器上对同一场景做前后对比采样。
